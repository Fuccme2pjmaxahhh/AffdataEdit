# 慢放音频分析（2026-11-08）

本次只分析现有变速路径，未替换音频后端，也未进行同一音源的录音 A/B。

## 当前实现

- `BassVoice` 用 `BASS_FX_TempoCreate` 建立变速流；`ArcAudioManager.PlayBackSpeed` 只设置属性 `0x10000`（tempo 百分比），没有设置额外的时间拉伸质量／窗口参数。
- BASS 输出初始化为 48000Hz，普通输出缓冲 100ms、更新周期 5ms，Windows 另有设备缓冲设置。单看这些数值不能证明是否发生欠载。
- 播放同步只校正内部谱面时钟，不在每帧对音频做 seek；当前源码不支持“同步每帧重定位撕裂”这一解释。

## 可进一步排查的处理路径

对照检查中还观察到 FMOD 频率控制配合原生 NStretch DSP 的方案：音频块交由 `NStretch.Process`，重置时调用 `NStretch.Reset`，并按 offset、倍率和采样率补偿时序。包装器与导出符号未标明底层算法，不能据此断言使用某个具体第三方库。

## 结论与界限

当前 BASS_FX Tempo 默认处理路径的拉伸算法与质量／窗口参数是低倍速音质问题的优先排查项。延迟补偿主要影响时序对齐，不能单凭它解释音质改善。未做录音与运行时欠载分析前，不能将严重撕裂唯一归因于算法，也不能认定加大缓冲就能解决。
